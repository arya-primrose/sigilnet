# DESIGN: the locator book (node id -> transport address, per transport), rev 0, 2026-10-03 (Arya). NOTHING BUILT. For Sansa's review, then the human's go.
Origin: live-test finding PF-1 (live_results/persist1/PREFLIGHT.md): a container's IP changed; the ping said "connect refused", and the repair needed a hand edit of tcp/held.json plus a restart. The principles and rules below were then decided; the go was to design the locator book now and address rotation afterwards (2026-10-03). Go scope: this DESIGN only. Building needs a separate go.

## 1. The decisions = the requirements
P1 All that matters to our protocol is that the messages coming across are correctly signed by a valid node identifier, not the transport address. Transport addresses can be transient. The transport level maps cryptographic node ids to network addresses, and each transport keeps its own book, which can be updated. Tor addresses can change too if the node wants.
P2 An agent must NEVER announce "here are all the possible ways to connect to me" (it would link an anonymous Tor identity to an IP). An agent MAY support two carriers at once (e.g. Sansa owns a thread and talks TCP with some agents and Tor with others); the human is still refining that.
P3 Dial rule: a thread owner attempts to communicate with other agents on the last good address it received from the agent. If a peer sends us a pull notification over TCP, even if it previously connected to us via Tor, we connect to it via TCP and switch to Tor only if TCP failed and only if we have a Tor address for it.
P4 (#1) The last good outbound carrier bumps that carrier to the top (so last good = the carrier of the last successful contact in EITHER direction). (#2) Fall back immediately if the primary carrier fails; if the secondary carrier fails, wait a timeout, then retry the primary and repeat the process; there should be 3 retries. (#3) Yes, this applies to all agents.

## 2. How it is today (code facts, r41_r0)
- Protocol layer (events, threads, sync, capsule) names agents by agent id (32 base32 chars = first 20 bytes of SHA-256(AGENT_CTX + signing public key)); every sync request is signed (`from`, `aud` = peer id, `ts`) and every reply is signed and checked against the id we meant to reach (a wrong id = "unsigned response").
- Addresses live in TWO node-level places: (a) `peers.json` (class `PeerBook`, node.py): agent id -> {name, endpoint {type, addr} or null, threads}: ONE endpoint per peer; (b) the carrier's credential store keyed by ENDPOINT ADDRESS: tcplink `held.json` {"ip:port#fp": {type, key}}; Tor: the client-auth key for an onion. `Carrier.use_credential(endpoint, secret)` / `drop_credential(endpoint)` take an endpoint, not an agent. This is why moving an address breaks authorization (PF-1).
- TCP endpoint = `ip:port#fp`: `fp` pins the door's TLS key; the client also proves a credential (public half authorized at the door; the peer door is bound to ONE agent id, `open_door(..., agent=)`). Tor endpoint = `<56>.onion:port`, the address IS the door key; client-auth key per onion.
- The node dials ONE endpoint per peer: `transport_for(rec)` = `carrier.dial(rec["endpoint"], ...)` (noderun.py). A failure goes through `_finish`: `unreachable` -> `down[peer]` with `backoff(tries)` (jittered, MAX_TRIES); pulls repeat every PULL_INTERVAL (300 s) anyway.
- `noderun` builds ONE carrier per node. Doors: one peer door per peer. A signed thread event kind `endpoint` exists (thread.py: `transports`: up to 8 {type, addr}) and `carrier.dial_candidates`, but NOTHING in production writes or reads it (only validation + tests). It is exactly the "all the ways to connect" list of P2; see Q5.
- Nothing records WHICH carrier or address last worked, and the source address of an inbound connection is dropped (tcplink accept: `conn, _ = sock.accept`; the sync server only ever sees loopback).

## 3. Design
### 3.1 The locator book, per carrier, keyed by node id
- Each carrier owns `home/<carrier>/book.json` (tcp/book.json, tor/book.json): `{agent_id: {"locators": [ {"addr": "...", "good_out": t|null, "fail": n, "seen": t}, ... max 4 ], "in_at": t|null, "cred": <the credential we hold for THEIR door, by node id>}}`. A locator is the carrier's address string (`ip:port#fp` / `x.onion:port`); `good_out` = last successful outbound dial; `in_at` = last authenticated inbound contact over THIS carrier from that agent (the carrier knows it: a peer door is bound to one agent id and the door authenticated the client before the protocol sees a byte).
- The credential is stored BY NODE ID (the key pair we use at their door), not by address: an address change moves nothing. `Carrier.use_credential(endpoint, secret, agent=None)`: with `agent` the key goes under the node id; without it (legacy) it stays keyed by address; `drop_credential` likewise. Tor: our client-auth key for a peer stays the same when the peer moves to a new onion (the peer authorizes the same PUBLIC client key at the new door, which it already holds).
- `peers.json` keeps name + threads (+ the old `endpoint` field as a SEED only, see 3.7). The node layer asks the carrier "dial agent X" and never handles addresses.
- At most 4 locators per agent per carrier; a new verified locator goes to the front, the oldest/most-failed is dropped.

### 3.2 Dial order (P3, P4)
For a peer, the locators across the node's carriers are ordered by the most recent GOOD CONTACT, in either direction: `max(good_out of the locator, in_at of its carrier)`; unknown = oldest. A dial walks the list: primary first; on failure it tries the next locator IMMEDIATELY (P4 #2). A success sets `good_out` (the locator and its carrier go to the top); an authenticated inbound contact sets `in_at` for that carrier (this is how "Sansa notified me over TCP" makes TCP primary even if the last pull went over Tor). Only locators the node actually holds are tried ("only if you had a Tor address for her").
- With one carrier and one locator this is exactly today's behaviour.
- With several locators (old and new IP on one carrier, or two carriers) the same code applies.

### 3.3 The retry cycle (P4 #2: "If secondary fails wait a timeout amount, then retry the primary and repeat. 3 retries.")
One CYCLE = try each held locator in order, no waiting between them. If every locator failed: the cycle failed. The node then waits `LOCATOR_WAIT` and starts a new cycle at the (re-ordered) top; at most 3 retries (up to 4 cycles) in a row. After the third retry fails the peer is `down` under the node's EXISTING backoff (so nothing is dropped; anti-entropy still tries every PULL_INTERVAL). A success resets the counter. Implementation: a per-peer `cycles` counter in node.json beside `down`, and the cycle wait is the job's `next` time (never a sleeping worker thread: one exchange per peer already holds the pool slot). PROPOSED defaults (to confirm): `LOCATOR_WAIT` = the failed attempt's connect timeout of its carrier (TCP short, Tor long), `LOCATOR_RETRIES = 3`. [My reading of the human's rule; the human can correct it.]

### 3.4 Updating a locator: the signed `locator` announcement (P1, P2)
- New sync request type `locator` {"t": "locator", "addr": "<carrier address of the door WE offer THIS peer>"}, signed like every request (`from`, `aud`, `ts`), sent by the node to a peer OVER THE CARRIER IT USES WITH THAT PEER, announcing ONLY the address of the door it opened for that peer on that carrier. It is never broadcast, never put in a thread, never lists more than one address, and never names another carrier: a peer that talks to us over TCP never hears our onion and the other way round (P2).
- WHEN: a new per-peer job kind `announce` beside pull/notify: due when the node's own door endpoint for that peer on that carrier differs from `announced[peer][carrier]` (persisted in node.json) and after a restart where it differs. Same retry/backoff machinery. Acknowledged = recorded.
- The one-IP-change case: Sansa's IP changes, her node starts, her door address for me differs from what she announced; she dials MY (unchanged) address, announces; I verify and adopt; the next pull from me goes to the new address. No human.
- Receiving side (sync server): after the normal authentication (the sender must be in the peer book, otherwise `srv.refuse` as for ping), check: the address type equals the carrier of THIS connection (the server is given its carrier type); `check_endpoint` (for TCP: valid `ip:port#fp`, private IP unless `allow_public`); one announcement per peer per `LOCATOR_MIN_GAP` (60 s), a signed `ts` newer than the last adopted announcement (replay of an old one is ignored); reply `ok` at once. The VERIFICATION and the adoption run in the node loop, NOT in the request handler (a dial takes seconds): the announcement is queued (bounded: one per peer).

### 3.5 Verification before adoption
The candidate is adopted only if a dial to it succeeds AND the answerer proves the same node id: the node sends a signed `ping` (already exists, nonce-bound, signed pong checked against the peer asked) over the candidate with our stored credential for that peer. TCP: the TLS `fp` pin in the address must match and the client proof must pass; Tor: the onion address is the door key and the peer must authorize our client key there. Verification failure: the candidate is discarded (counted; 3 failures from one peer in an hour = its announcements are ignored for an hour, logged). A successful verification IS an outbound success: the new locator goes to the top.

### 3.6 Manual repair and display
- `sigilnet peer move AGENT_ID --endpoint TYPE:ADDR [--no-verify]`: adds the locator (to the carrier book of its type) with the same verification; `--no-verify` only for the case where the peer is not up yet. Needed when BOTH sides' addresses changed (neither can announce to the other): each side runs `peer move` with the address the human relays.
- `peer list` shows all held locators per peer, primary first, with "last good N s ago"; `ping` says which locator answered; history.log gets `locator <name>: adopted tcp 10.0.0.4:47700 (verified)` / `discarded (<why>)` (no text of peers, ids and counts only, as today).

### 3.7 Migration and rollback
First start of new code: for each peer with `endpoint` in peers.json, the carrier of that type gets a book entry (the endpoint as the first locator, `good_out` unknown) and tcp `held.json` entries are re-keyed by the node id of the peer whose endpoint address they belong to (an entry that matches no peer stays keyed by address). `peers.json` keeps its `endpoint` field, written again by `peer add`/`peer move` for the PRIMARY locator, so old code on a migrated home still dials something (rollback: old code ignores the book). Idempotent, under the same file locks as today; refuses nothing; a damaged book is rebuilt from peers.json.

## 4. Staging (recommendation)
- **S1 = this design with ONE carrier per node:** book per carrier by node id, credential by node id, dial over several locators of that carrier (old+new IP), `locator` announcement + verification, retry cycle, `peer move`/`peer list`, migration. This alone removes PF-1 (one IP changes: automatic; both change: `peer move` by hand) and is needed for everything else.
- **S2 = a node that runs SEVERAL carriers at once** (noderun holds a carrier set; peer doors per carrier; capsule picks the carrier by the endpoint type; inbound `in_at` per carrier; cross-carrier dial order). The ordering and cycle rules above already cover it, but S2 changes noderun, doors, capsule and the tor+tcp co-existence tests and the human is still refining it: NOT proposed for building now. S1 must not make S2 harder (the book is per carrier, keyed by node id).

## 5. Risks and what a hostile peer can do
1. **A (valid, authenticated) peer makes my node dial an address of its choosing** (verification dial): bounded to one per peer per 60 s, private IPs only (TCP), 3 failures per hour then ignored, the dial is a TLS handshake that fails on the pin; residual: a compromised peer can make us probe private-LAN `ip:port`s slowly. Q4: restrict adoption to the /16 of the current locator?
2. **Hijack by a bad announcement** (valid sender announces an address it does not control): verification requires the answerer to prove the SENDER's node id, so only the sender (or whoever holds its key) can pass.
3. **Replay of an old announcement**: signed `ts` must be newer than the last adopted; the 4-locator cap and the verification make a stale address harmless (it fails and is dropped).
4. **Flapping between carriers**: ordering by last good contact can swap primaries on every alternation; the retry cycle only waits when ALL fail; no hysteresis is proposed (the human's rule is last-good-first). Q3.
5. **Linkability (P2)**: only the pairwise knowledge a peer already has; the announcement names the one carrier in use; the thread `endpoint` event (list of up to 8) is NOT used (Q5).
6. **Both addresses change**: not solvable automatically (no one can reach the other to announce); `peer move` with an out-of-band address; with `arya_link` stopped, the human is the channel.

## Rev 1 (2026-10-03 ~: Sansa's review (design APPROVED for S1 with F1-F3), all accepted; overrides rev 0 where it differs

The explicit-IP form stays valid. Tests: change B's IP, restart with `auto`, A learns the new address (the PF-1 scenario as an automated test). - **F2 (the human's minimal repair):** both-change is NOT rare (containers restarted together get new IPs). `sigilnet peer move AGENT --ip NEWIP` keeps the old port and `#fp` (only the IP changed; doors.json persists the door key and port); the full `--endpoint TYPE:ADDR` stays for everything else.
