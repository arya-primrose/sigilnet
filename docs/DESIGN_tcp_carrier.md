## 1. Contract fit (carrier.py)
Same contract as TorNode / FakeCarrier; protocol modules unchanged; only noderun's composition root learns a switch `node_config.json: {"carrier": "tcp", "tcp": {"bind": "10.0.0.3", "port_base": 47600}}` (default stays tor). capabilities = frozenset (NO "hides_ip": public doors (read, inbox) are refused unless --allow-public-without-ip-hiding, exactly as doors.py already does).
Types: endpoint `{"type":"tcp","addr":"<ipv4>:<port>#<door-fp 64 hex>"}` (<=256, validated by the carrier; IPv4 private/loopback only unless `allow_public: true` in the config, which I would take to the human). credential `{"type":"tcp","key":"<64 hex>"}`: PUBLIC key = sha256 of the client's Ed25519 public key; SECRET key = the 32-byte Ed25519 seed (64 hex). capsule.py already compares carrier types only (checked: no onion-specific code in it).

## 2. Wire security (the carrier must do what Tor did for free: encrypt, authenticate the door, admit only the authorized client)
Layer 1: TLS 1.3 (python ssl, no custom crypto record layer). The door has a long-lived self-signed Ed25519/ECDSA certificate; the dialer PINS the door's key: `#<door-fp>` in the endpoint = sha256 of the cert's SPKI; the client verifies it after the handshake (verify_mode CERT_NONE + explicit fingerprint compare, hostname ignored). TLS gives confidentiality + server authentication; no CA.
Layer 2: client admission by signature inside the TLS channel: server sends 32 random bytes; the client replies {pub, sig} with sig = Ed25519(seed, "sigilnet-tcp-auth-1" || nonce || door-fp || client-pub-fp); the door checks sha256(pub) equals the PUBLIC credential it holds for this door (peer/join doors admit exactly ONE credential). Including door-fp stops a malicious door relaying the auth to another door; the nonce stops replay. Any failure (bad TLS, no auth in 5 s, wrong key) closes the socket with NO reply bytes (an unauthorized client reaches nothing).
Then the carrier pipes the decrypted stream to the loopback port that open_door returned, where the PROTOCOL's guarded TcpServer (plain mode) answers: framing, size caps, deadlines, signatures per request are unchanged (same as Tor plain mode).
Why not reuse tcp.py's Fernet pairwise key? It is one shared SYMMETRIC key: there is no public/secret split, so the "public credential" in a join request would equal the secret. TLS+signature keeps the contract's asymmetric credentials.
Public doors (read/inbox, no credential): TLS only (pinned fp), no layer 2, same loopback pipe.

## 3. State and processes (TorNode parity)
`home/tcp/`: `doors.json` (name -> kind, agent, loopback port, listen port, auth public fp), `door-<name>.key` (0600, the door's TLS key; deleted with the door: door_gone verifies entry AND key file are gone), `held.json` (0600: secrets we hold for THEIR doors, keyed by endpoint addr), flock for cross-process edits. The CLI creates/removes doors in its own process (as with tor services.json); a running node picks changes up in `reconfigure` (called by doors.sync every tick): opens/closes listening sockets. Listen ports are assigned once from port_base and persisted (stable endpoint across restarts, like an onion address). Per-door cap on concurrent streams (default 8) and an accept timeout for the auth step.
start: bind all door listeners on `bind`; a bind failure is CarrierError(retry=False). healthy: accept threads alive. S1's restart logic then works unchanged (stop+start rebinds the same ports; peers reconnect at once: no HS-publication delay).
dial: connect (connect_timeout), TLS, check pin, layer-2 reply if a credential is held, return a TcpTransport-compatible object whose request uses the same frames as TorTransport (subclass `_connect`, as TorTransport does).

## R1. Names and constructor (frozen)
- Module `sigilnet/tcplink.py`; class `TcpCarrier(Carrier)`; `TcpCarrier.type == "tcp"`; `capabilities == frozenset`. Imports only carrier, tcp (frames/limits), keys (verify_strict, AGENT_ID_RE), stdlib (ssl, socket, threading, hmac, hashlib, json, os, fcntl, ipaddress) and `cryptography` (x509/ec for the door cert, Ed25519 for the client key; both already used by keys.py/Fernet).
- `TcpCarrier(state_dir: Path, *, bind: str, port_base: int, advertise: str | None = None, allow_public: bool = False, max_streams_per_door: int = 8, max_unauth: int = 32, auth_deadline: float = 5.0, pipe_idle: float = 120.0, pipe_total: float = 600.0)`. `bind` and `advertise` (default = bind) are dotted-quad IPv4 strings; `port_base` is an int with 1024 <= port_base <= 64000. ValueError for anything else, and for a bind/advertise that is not private/loopback (ipaddress is_private or is_loopback, and not unspecified) unless `allow_public=True`. 0.0.0.0 is never accepted, even with allow_public.
- Node config (`node_config.json`, validated by noderun.load_config like the other keys): `"carrier": "tor" | "tcp"` (default "tor"), and for tcp `"tcp": {"bind": str, "port_base": int, "advertise": str (optional), "allow_public": bool (optional, default false)}`. Unknown keys inside "tcp" are an error. `noderun.make_carrier(home, cfg, offline)` picks the class (`tor_node` stays as the Tor branch); state dir `home/tcp`.
- Ports (deterministic): a persistent counter `next_index` in doors.json; door number i (never reused after a close) listens on `bind:(port_base+2*i)` and its protocol server listens on `127.0.0.1:(port_base+2*i+1)` (that second port is what `open_door` returns). 2*i+1 must stay < 65536-port_base else ValueError("too many doors").

## R2. Formats and validation (frozen)
- Endpoint `{"type":"tcp","addr":A}` with A = `<ip>:<port>#<fp>`: `ip` canonical dotted-quad IPv4 (four decimal octets 0-255, no leading zeros), `port` decimal 1-65535 without leading zeros, `fp` = exactly 64 lowercase hex (the sha256 of the door certificate's SubjectPublicKeyInfo DER). `check_addr` is a pure FORMAT check registered with `carrier.register_type("tcp", ...)`; it lowercases and strips surrounding whitespace first (like fake/onion) and raises ValueError otherwise. The private/loopback rule is enforced by the carrier (dial refuses a non-private ip unless allow_public: CarrierError(retry=False)), not by the format check.
- Credential `{"type":"tcp","key":K}` with K exactly 64 lowercase hex. PUBLIC key = hex(sha256(raw 32-byte Ed25519 public key)); SECRET key = hex(32-byte Ed25519 seed). `new_credential` returns (Secret({"type":"tcp","key":seed_hex}), {"type":"tcp","key":sha256(pub)_hex}).
- Door TLS key: ECDSA P-256 (a different algorithm from every Ed25519 key in the system on purpose), generated per door at `open_door`, stored with its self-signed certificate (CN "sigilnet-tcp", validity 100 years, regenerated on demand: the pin is the SPKI hash so a cert can be re-issued for the same key). A re-key of a door = a new key = a NEW endpoint (the old pin no longer matches). The door TLS key is never derived from or equal to an identity, auth or any other key.

## R3. Wire (frozen), per connection
0. TCP connect. Client socket timeout set BEFORE wrapping; the door applies ONE deadline `auth_deadline` from accept covering handshake + admission.
1. TLS: both sides exactly TLS 1.3 (`minimum_version = maximum_version = TLSv1_3`), `OP_NO_TICKET` (no resumption), no client certificate, no ALPN, no SNI (`server_hostname=None`, `check_hostname=False`, `verify_mode=CERT_NONE` plus the explicit pin check), library-default 1.3 cipher suites. After the handshake the client computes sha256(SPKI DER of the peer cert) and compares with the endpoint's fp using hmac.compare_digest BEFORE sending any application byte; mismatch -> close, CarrierError("door key does not match the endpoint", retry=False).
2. Door -> client, always, exactly 39 bytes: `b"SNTCP1"` (6) || mode (1 byte: 0x00 public door, 0x01 admission required) || nonce (32 bytes from os.urandom; present for both modes). The client reads exactly 39 bytes; any other prefix/short read -> CarrierError(retry=True).
   Client checks the mode against what it holds: mode 0x01 and no credential held -> CarrierError("the door needs a credential", retry=False); mode 0x00 -> no credential is sent (and none is needed).
3. Only if mode 0x01. Client -> door, exactly 96 bytes: `pub` (32, Ed25519 public key) || `sig` (64). `sig = Ed25519(seed, M)` with M = for each of [b"sigilnet-tcp-auth-1", nonce, door_fp_bytes (32 raw bytes of the endpoint's fp), sha256(pub)] a 2-byte big-endian length followed by the bytes, concatenated. The door: reads exactly 96 bytes within the deadline; computes h = sha256(pub); `hmac.compare_digest(h, door.auth_fp)`; checks `keys.verify_strict` (rejects non-canonical/small-order); if all pass sends ONE byte `0x01` and continues; on ANY failure it closes the socket immediately and sends nothing (no application bytes: the TLS handshake itself still reveals a TLS service and its cert, an accepted limit like capabilities=empty).
   The client: reads exactly 1 byte; `0x01` = admitted; EOF/timeout/other -> CarrierError("not admitted (or the door went away)", retry=True) (not False: a restarting door must not wedge a peer job; the Node's backoff is the throttle).
4. Pipe: the door connects to `127.0.0.1:<loopback port>` (connect timeout 2 s; failure -> close) and pumps bytes both ways. The stream carried is the PROTOCOL's own frames (tcp._frame plain mode, no Fernet), one request frame then one response frame, exactly as over Tor. Caps per direction per connection: client->backend `tcp.MAX_REQ + 64` bytes, backend->client `tcp.MAX_RESP + 64` bytes (a connection exceeding it is closed); idle deadline `pipe_idle` (no bytes in either direction), total deadline `pipe_total`; half-close (shutdown(SHUT_WR)) is forwarded; both pump threads are joined on close; a stalled backend frees its slot at the deadlines.
5. Limits: at most `max_unauth` sockets not yet admitted at any time across all doors (over the cap: accept and close at once, before TLS), and at most `max_streams_per_door` admitted streams per door (over: close). The protocol server behind the loopback port sees only 127.0.0.1: no per-IP policy exists there (same as Tor).
Not bound to the TLS session (stdlib has no exporter; tls-unique does not exist in 1.3): protection against relaying is the door fp inside the signed message + the pin checked first. Residual: a door the client chose to trust can relay the client's admission only to ITSELF.

## R4. Exceptions (frozen) `CarrierError(msg, retry)`
retry=False: malformed/unsupported endpoint or credential; non-private ip without allow_public (dial) ; pin mismatch; door needs a credential and none is held; a held credential is for another door (use_credential keys by the full addr); door kind mismatch on open_door. retry=True: connect refused/timeout, TLS handshake error or timeout, short read of the 39-byte hello, not admitted / EOF after the auth message, backend unreachable (seen as EOF), carrier not started. `ValueError`: bad names/kinds/credential shapes/bind config (same texts as torlink/fake where they exist). `start` on a port that cannot be bound: CarrierError(retry=False) naming the port.

## R5. Doors and state (frozen)
`state_dir = home/tcp`: `doors.json` (0600, atomic tmp+rename, flock on `state.lock`): `{"version":1,"next_index":N,"doors":{NAME:{"kind","agent","index","listen_port","loopback_port","auth": <public cred key or null>,"fp": <door spki fp>}}}`; `door-NAME.pem` (0600, O_EXCL tmp+rename: TLS private key + cert); `held.json` (0600, same write rule): `{ "<full addr incl #fp>": {"type":"tcp","key": seed_hex} }`. `open_door`: name regex `[a-z0-9_-]{1,32}`, kinds `carrier.KINDS`; public kinds take no credential and no agent, client-authorized kinds (peer, join) need the PUBLIC credential; agent only on peer doors (AGENT_ID_RE); re-opening an existing name of the same kind re-keys its `auth` (same index, ports and TLS key) ; a different kind -> ValueError. `close_door` removes the entry; the key file is removed in the same locked step; `door_gone(name)` is True only if no entry AND no `door-NAME.pem`. `door_endpoint(name)` = `{"type":"tcp","addr":f"{advertise}:{listen_port}#{fp}"}` once the door exists (no start needed: addresses are deterministic). `doors` = `{name: {"kind","agent","port": loopback_port}}`. `reconfigure` re-reads doors.json under the lock and opens/closes the listeners of a running carrier (True if it changed anything; a no-op when not started). `healthy` = started and every accept thread alive. `stop` closes listeners and all streams and joins threads (idempotent); `start` after `stop` rebinds the SAME ports (S1 restart path); `shared_endpoint/shared_port` = None.
`use_credential(endpoint, secret)`: stores the seed under the full normalized addr; `drop_credential` removes it. Secrets are never in any log, repr or exception text (Secret repr). Multi-process: the CLI may call open_door/close_door/new_credential/use_credential on a TcpCarrier that is NOT started (state-only) while a node runs.

# REVISION 1.1 (2026-10-01 ~; answers to Sansa's A1-A13, 939061ce96b8; binding like rev 1; where it differs, 1.1 wins)
- A1 Bytes the client sends before the hello is read just queue in TLS; they are never "garbage" by themselves. Mode 1: the door reads EXACTLY 96 bytes after the hello; anything the client sends before that is part of those 96 (wrong => close, no byte). Bytes after the 96 (a client that pipelines its request frame behind the auth without waiting for 0x01) are request data: they are forwarded to the backend only AFTER admission and the stream-cap check; the backend's own guard judges them. Mode 0: everything the client sends is piped (the protocol's guard judges it). Nothing is forwarded to the backend before admission.
- A2 A TLS alert or close_notify on failure is allowed (OpenSSL sends alerts on handshake errors; the door also just shuts the TCP socket). The invariant to test: NO application-data record is ever sent by the door on a failed admission (no hello is withheld: the hello IS sent before admission, it is 39 bytes of public data; the failure invariant is "no 0x01 and no backend bytes").  <- clarification: the hello (39 bytes, mode+nonce) is application data the door sends to ANY client that completed TLS; only the 0x01 and later bytes are withheld on failure.
- A3 Mode byte not in {0,1}: CarrierError(retry=True), same as a bad prefix. A client that holds a credential for the endpoint and meets mode 0 proceeds and sends NOTHING (the pin makes the door authentic; a door that wants no admission is its own business).
- A4 The stream cap is checked BEFORE the 0x01 byte: over the cap = socket closed with no 0x01 (mode 0: closed before piping). The unauth slot is released the moment the connection becomes a stream (cap passed) or the connection ends for any reason (handshake error, timeout, bad auth, cap): never leaked; the counters are decremented exactly once per connection.
- A5 Re-key (open_door same name, new auth): NEW connections only; live streams finish at their own deadlines. close_door: when a running carrier (in ANOTHER process) next calls reconfigure, the door's listener closes AND its live streams are shut down (revocation is immediate); a connection that completed TLS but was not yet admitted when the door disappeared from doors.json gets nothing further (the door entry is re-read after the handshake; missing or re-created under another index => close). The door entry (auth) is re-read per connection, so a revoked/re-keyed credential is refused even before reconfigure.
- A6 Stored ports win: existing doors keep listen_port/loopback_port from doors.json; `port_base` only numbers NEW doors; `advertise` only changes the ip in door_endpoint (fp and port unchanged); `bind` is where listeners bind (a stored port outside the new port_base range is used as stored).
- A7 start: idempotent when already started; `wait` is ignored; if any door cannot be bound, every listener already bound is closed again (stop), `started` is False and CarrierError(retry=False) names the port. A door whose door-NAME.pem is missing/damaged fails start the same way.
- A8 CORRECTION: there is NO certificate regeneration in rev 1 (rev 0 text withdrawn). The pem (key + cert, validity 100 years) is made once at open_door. A missing/corrupt key half or cert half => start raises CarrierError(retry=False) (test: truncate the cert half). The SPKI pin would allow re-issuing a cert for the same key later; not implemented.
- A9 Caps count bytes per connection after admission. Exactly PIPE_UP (= tcp.MAX_REQ + 64) bytes client->backend pass; the first byte beyond ends the connection (the allowed prefix is forwarded, the rest dropped). Same for PIPE_DOWN (= tcp.MAX_RESP + 64) backend->client.
- A10 Yes: held.json is keyed by the carrier-normalized addr (strip + lower via check_endpoint); case/space variants hit the same key. drop_credential returns True only if one was held (and rewrites held.json then).
- A11 doors, door_endpoint, door_gone read doors.json fresh on every call (never the running carrier's memory).
- A12 open_door returns the loopback port (int, port_base+2i+1); re-opening an existing door returns the same port.
- A13 dial is lazy like torlink's: it validates the endpoint (CarrierError retry=False for malformed/unsupported/non-private) and returns a transport; nothing connects until request. In request: if `connect_timeout` is given it is the budget for connect + TLS + hello + admission and `timeout` starts after that; otherwise ONE budget `timeout` covers everything (exactly TcpTransport's rule that TorTransport also uses). Exceptions from request: CarrierError (retry per R4) for connect/TLS/admission failures; ConnectionError("no valid response") for a backend EOF/invalid frame (inherited from TcpTransport, same as Tor); ValueError("request too large"). The only intended difference from TorTransport is the class of CarrierError (carrier.CarrierError itself, not TorError).

## Limit added 2026-10-02 (the human's point): endpoints embed an IP
Container IPs on the docker bridge are assigned at start and can change when containers restart; a tcp endpoint (and arya_link's stored direct_peer) then points at nothing, while an onion address is tied to the service key and survives. So: (1) rev 1 stays a LAN/same-network carrier; (2) the bake-off gets a criterion "survives an address change"; (3) the longer-term shape is a node that publishes SEVERAL transports (tcp fast path + onion stable fallback; the signed endpoint event already carries a transports list and dial_candidates already tries them in the author's order); today a node runs ONE carrier (noderun.make_carrier), a multi-carrier node would be a separate design.
