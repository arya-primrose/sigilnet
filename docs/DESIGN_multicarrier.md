# DESIGN: several carriers in one node (S2: tcp + tor at once), rev 3 (see the end: SHARED DOORS DROPPED, per-peer doors stay), 2026-10-04 (Arya). NOTHING BUILT except M0/M0b (live). For the human, then Sansa's review.
Origin (2026-10-04): both agents should be capable of running both tor and tcp; a node can run 2 carriers and be contacted over either at any time, the only requirement being that it responds on the last-known-good carrier; not announcing all carriers is the node protecting its identity (no directory/lookup in the protocol); an anonymous node contacts peers only over Tor. Decisions (answers to my six questions): (1) cross-carrier announcement DEFERRED: for now the address would just be announced in the thread (everyone in it could see it), no official protocol needed. (3) invitation capsules can include as many carriers as the issuing agent/node chooses; it has no obligation to announce all carriers it supports. (4) tcp addresses need not be private: any ip address is allowed (loopback, local or public). (5) throwaway live Tor tests are fine; the two agents need a stable tor address so they keep communicating even if their IPs change. (6) nothing binds a thread to a carrier; a test that alternates tor/tcp every other message is wanted. DOORS: a door per peer node is heavy, so use the door per-carrier option (B) (later withdrawn, see Rev 3). Building and each deploy need their own go.

## 1. As built today (r45b)
- ONE carrier per node: `noderun.make_carrier` picks `tor` or `tcp` from `node_config.json` (`"carrier": "tcp"`); `run` holds one `tor` variable, ONE `LocatorBook` (`locators/<type>.json`), one `PeerDialer(carrier, book)`, one `LocatorService`, `Doors(carrier, syncsrv)`, the capsule code and the status line all take that one carrier.
- DOORS are per peer: `open_door(name, kind, credential, agent)`. TCP: each door = its own listening port (`port_base + 2i`), its own TLS key (`fp`), one authorized Ed25519 admission key, bound to one agent; the carrier forwards to that door's loopback port, where `doors.service_handler(srv, agent)` refuses any request whose `from` is not the bound agent. Tor: each door = its OWN onion service (own address, own client-auth key), forwarded to its loopback port, same handler. Live today: a `peer-nadnoh4j…` door (port 47704) for Sansa and a `human` door (47700) for the observer seat. A legacy `shared_port` (one onion without per-peer binding) exists in the Tor code.
- Private-only guards for TCP in `tcplink.py`: `_check_ip` (bind/advertise), `locator_problem` (announced addresses), `dial` (`not _is_private(ip) and not allow_public`), `resolve_bind`; config `allow_public`.
- `in_at` (last authenticated INBOUND contact per carrier) was in DESIGN_locator_book.md rev 1 section 3.2 but is NOT in the code; today only `good_out` (last good dial) orders addresses.

## 2. Design
### 2.1 A carrier set (M1)
- `node_config.json`: `"carriers": ["tcp", "onion"]` (the old `"carrier": "tcp"` still means a set of one: an old home starts as before). A node that wants to stay anonymous configures only `["onion"]`: it has no TCP carrier, so it can never dial or listen on TCP (the node's choice, not a protocol rule).
- `run` builds `{type: carrier}`; each carrier has its own `LocatorBook` (`locators/tcp.json`, `locators/onion.json`: already per type), its own doors, its own health check and `_recover_carrier`, its own `LocatorService`. `Node` and `PingService` get ONE `MultiDialer` instead of one `PeerDialer`.
- `status`/`ping` print which carrier answered. Nothing in any message, thread or answer lists the carriers a node runs (no directory): a peer learns an address only from what the node itself chooses to tell it.

### 2.2 Doors, option B: ONE shared peer door per carrier (M1)  [SUPERSEDED BY REV 3: the human dropped shared doors; per-peer doors stay as built. Kept as history; do not build it.]
- **TCP:** one public listener (one port, one TLS key `fp`, so ONE stable endpoint `ip:port#fp` for everybody). Admission as today (96 bytes `pub(32)+sig(64)` over [domain, nonce, door fp, sha256(pub)]) but the door holds a TABLE `{admission pub -> agent id}` instead of one key. On a good admission the carrier forwards the connection to the loopback port of THAT agent (one loopback `TcpServer` per table entry, each with `service_handler(srv, agent)` exactly as now). So the door-level agent binding is KEPT on TCP, loopback listeners are cheap, and the public side needs one port. New Carrier methods: `authorize(door, credential, agent) -> loopback port`, `revoke(door, agent) -> bool`, `clients(door)`. Revocation = remove the entry (no key change; everyone else is untouched).
- **Tor:** one onion service for peers (one stable `.onion`), v3 client authorization with MANY authorized client keys (`authorized_clients/` holds one file per peer). Tor does NOT tell the application which client key connected, so every client reaches the same loopback port, handled with `agent=None`: the agent binding at the door is LOST on Tor (the per-request signature and `SyncServer._authenticate` stay the gate: `from` must be a member of the thread or a peer; a stolen client-auth key alone still cannot sign as an agent). Revocation = remove that peer's authorized-client file and reload (the onion address stays).
- **Stranger doors** (read, inbox, join) are already one per carrier: unchanged.
- **Migration:** additive. Existing per-peer doors keep working (the live pair is not touched); the shared door is created when `carriers` is configured or by `sigilnet door shared --carrier tcp`; a peer can be moved to it later by giving that peer the shared address (a thread post, 2.5) and closing its old door. The new code reads old and new doors.

### 2.3 Dial order and "answer on the last-known-good carrier" (M1)
- A `MultiDialer` collects a peer's locators from every carrier's book and orders them by the most recent good contact in EITHER direction: `max(good_out, in_at)` (human's P3/P4, DESIGN_locator_book.md 3.2). New: `in_at`. The SyncServer is told which carrier a request arrived on (the door handler closure carries the carrier type, as it carries the bound agent now); AFTER `_authenticate` succeeds it calls `book.note_inbound(agent)` on that carrier's book (cheap, throttled like `note_ok`).
- The pull that follows a `notify` therefore goes back over the carrier the notify came in on.
- The retry cycle of 3.3 generalizes: one cycle tries each carrier's primary locator in order with no wait; if all fail, wait `LOCATOR_WAIT`, repeat, at most 3 retries; then the node's existing `down`/backoff. With one carrier and one locator it is today's behaviour.
- A carrier that is down (tor still bootstrapping) is skipped without blocking the others: the node starts serving on whichever carrier is up.

### 2.4 Any IP address (M3; the human's point 4)
- Remove the private-only rule: `_check_ip`, `locator_problem` (keep: well-formed, not our own door), `dial`, `resolve_bind` ("auto" still prefers the interface that routes to a peer; `bind` may be an explicit address or `0.0.0.0`), `allow_public` is dropped (a config that still has it is accepted and ignored). `advertise` (the address put into the endpoint when it differs from the bind, e.g. a public IP behind NAT) stays and is required to be set by the operator when `bind` is not the address peers use.
- NOT changed: the `allow_public_without_ip_hiding` switch of `Doors` is about STRANGER doors (read/inbox) that publish an address on a carrier that does not hide the host: separate question, stays.
- Risks to review (Sansa): (a) a public TLS listener can be scanned and handshaked by anyone (documented: the carrier does not hide that a TLS service exists); the pre-admission cost per connection must be bounded per source IP BEFORE the handshake: today the per-IP guards (`tcp.py` `per_ip`) sit on the LOOPBACK server behind the carrier, where every connection comes from 127.0.0.1, so a per-source-IP limit in `tcplink.py` at accept time is NEW work and part of M3; (b) the `locator` verification dial (any member can make my node open a TLS handshake to an address of its choosing): already bounded to one announcement per 60 s per peer and 3 failures per hour; with public IPs allowed the target space is the Internet: accepted risk or restrict?; (c) a public IP in an announcement links that agent id to that IP for the readers of the thread (the human's accepted trade-off, interim).

### 2.5 Learning an address of another carrier (deferred by the human)
- NO new protocol. Interim: the owner posts the address in the thread as ordinary text (a convention), and each reader applies it with the existing `sigilnet peer move AGENT_ID --endpoint tcp:ADDR` (it adds a locator to the book of that TYPE; with M1 both types can exist for one peer). The in-protocol `locator` request keeps working for the carrier it arrives on; relaxing "type == carrier of this connection" is the deferred question. TCP inbound source-IP learning: also deferred.

### 2.6 Capsules (M2)
- A capsule carries a LIST of join endpoints (`endpoints`), one per carrier the issuer chose (`capsule new --carrier tcp --carrier onion`; default: the node's first carrier only); the joiner tries them in the issuer's order. No obligation to list all; the format version is bumped and a single-endpoint capsule still reads. Needs a join door per listed carrier.

### 2.7 A stable Tor address (the human's point 5)
- One onion service for peers per node (2.2) whose hidden-service key lives in the Tor data directory under the node home; the address survives IP changes (that is the point). The key is backed up like the identity key (`<backup dir> 0600), because a lost key is a new address that nobody knows. A throwaway test onion is separate. Running Tor on the LIVE nodes publishes a descriptor to the Tor network: that waits for the human's separate go, after the tests pass.

### 2.8 Staging
M1 carrier set + shared doors + `in_at` + MultiDialer (the core; includes tcp+tcp-loopback two-carrier tests and real tor); M2 capsules with several endpoints; M3 any IP (+ per-source-IP guard); M4 the alternating test (below). Each: design reviewed, then its own build go, Sansa reviews first and deploys first.

### 2.9 Push on dial (hole 1: a member nobody can dial could not publish)
- Today only role `guest` can push (through the inbox door); every member's events reach another node only because THAT node dials the author and pulls. A firewalled TCP peer, an outbound-only node or a future UDP peer is therefore a one-way reader. Fix at the PROTOCOL layer (carrier independent): the node that DIALS also pushes.
- New sync request `{"t": "push", "thread": T, "events": [<signed events, dependency order>]}`, signed and audience-bound like every sync request, sent over the connection the dialer opened. The dialer learns what the peer lacks from the `summary` it already fetches in a pull, and pushes those of its own stored events (its own and others': a relay of what it holds is fine, every event is self-verifying).
- Receiver: the sender must be a CURRENT member (any actor role; an observer can still not push); each event goes through the same `Mirror.ingest` as a pulled event (signature, thread rules, rate rules, parking of events whose parents are missing); the answer is a signed list of per-event results (accepted / duplicate / rejected: reason). It wakes like a pulled event (`inbox.jsonl` pointers). Nothing is trusted because it was pushed. Limits: at most N events and B bytes per request, a token bucket per (peer, thread), and the existing MAX_STORED.
- Result: an outbound-only peer polls (dial, pull what I have, push what it has): both directions over ONE connection it opened; nothing is needed from my side to reach it. Notifies only make it poll sooner (2.10).
- OPEN, same hole for BLOBS: an attachment is fetched from the author with a `blob` request, i.e. by dialing it. For an undialable author: blob push (a `blob_push` request, hash-checked chunks) or relay by a member that holds the blob. Not decided; the design must say before M1 ships push.
### 2.10 The notify address (hole 3, replaces "learning the other carrier's address" for notifies)
- A request MAY carry an optional signed field `notify_at` {"type": "tcp", "addr": "..."}: the address where THIS peer wants notifies. The receiving host remembers the LAST one per (peer, carrier type) in its locator book as a NOTIFY locator (kept apart from the pull locators; never announced to anybody else). Notify jobs dial it; if none is known, or it fails (a few failures drop it), no notify is sent and the peer is simply expected to poll (its pull and push cycle, PULL_INTERVAL 300 s). A peer that omits the field changes nothing, and an old node ignores the key only if the request validator allows it: the field must be added to the allowed keys of the signed envelope on BOTH sides first (version gate for the deploy, Sansa first).
- It carries a carrier address, so it is type-checked by the carrier like any locator (any IP allowed since point 4; each notify dial is bounded: one per peer per `NOTIFY_MIN_GAP`, 3 failures drop the address). It is NOT verified by a ping dial before use (a bad one just fails and is dropped); a notify is a hint that carries no text.
- This also gives the "start on Tor, supply a TCP notify address later" path the human wanted, with no directory: the address goes to ONE host, inside a signed request, only when the peer chooses.
### 2.3 amended: backoff per (peer, carrier)
- `Node.down`, its backoff and the retry cycle are keyed by (peer, carrier type): a carrier that fails does not mark the peer down for the other one; the peer is `down` only when every carrier with a held address is down.
### 2.2 amended: no capability flags for now (the human); the Carrier interface does not change for that.
### Hole 5 (checked 2026-10-04, read-only): what removing a member does to doors
- `remove THREAD AGENT` writes only the signed `member_remove` event (thread level). It does not close the door or revoke the carrier credential. `peer rm` drops OUR credential for that peer and its book entries; the door WE gave THEM stays until `node revoke NAME` (a separate manual command); capsule teardown closes only the one-time join door. So a removed or forgotten peer can still connect and handshake; the thread gate still holds (the sync server answers only members of a thread; a ping needs the peer in `peers.json`, which `peer rm` removes). With B (shared door, one table) the equivalent is a stale credential-to-agent entry. Proposed: `peer rm` also revokes the door/table entry we gave that peer (a node-level act, confirmed by the owner), and `list` shows doors with no peer. Not tested against a live removed member yet.
### Hole 6 (open): see the human's question; what a public TCP listener needs. As built the TCP door has only a global cap on concurrent unauthenticated connections (`max_unauth` 32, `auth_deadline` 5 s) and no per-source-IP limit.

### 2.4a Proposed numbers for the public TCP listener (M3), to be reviewed by Sansa
Principle: limit what FAILS admission, never what succeeds (a legitimate peer makes one connection per request, hundreds per blob fetch, so a per-IP total cap would hurt real peers).
- At accept, BEFORE the TLS handshake: per source address (IPv4 /32, IPv6 /64): at most 4 concurrent unauthenticated connections; over the limit the socket is closed at once, no handshake.
- A connection that does not complete admission (handshake failure, wrong key, timeout) is a STRIKE for its address: 10 strikes in 60 s = that address is refused at accept for 60 s (doubling on repeat, max 1 h; a successful admission clears the strikes).
- Reserve: of the global `max_unauth` 32, 16 slots only for addresses that completed an admission in the last 10 minutes, so strangers can never starve peers that already proved themselves.
- The tables are bounded (4096 addresses, least recently seen dropped); a `status` line counts refused-at-accept connections (counts only, no addresses in history.log).
- `auth_deadline` stays 5 s. Addresses a peer gives us to dial (`locator`, `notify_at`): one dial per peer per 60 s, 3 failures drop the address (as designed).

### 3.2 What M1 is now (smaller)
- A carrier SET (`"carriers": ["tcp", "onion"]`, old `"carrier"` = a set of one). - Two doors for one peer on the SAME carrier type (old and new) already works since M0b (dial: address entry first, then `agent:<id>`).
### 3.3 Peer-supplied addresses (Sansa F5, F6; any IP stays allowed for what the OPERATOR types)
- An address a PEER supplies (`locator`, `notify_at`) always refuses loopback (unless we bind loopback ourselves), link-local (169.254/16, includes the cloud metadata address), unspecified, multicast, broadcast, port 0; private and public are allowed. The announcer never sees the verification result or a `refused: why` detail (a probe, not an oracle).
- [SUPERSEDED BY D1 (rev 4 resolution): cross-carrier notify_at is ALLOWED, no per-peer policy; do NOT build this rule] `notify_at` must be of the carrier type it ARRIVED on, unless the receiver has set a per-peer policy (`peer move AGENT --endpoint tcp:...` is already such an opt-in by the operator): otherwise a peer I only know over Tor makes my node dial TCP from my real IP (F6). One notify address per (peer, carrier); the 3-failure drop is per (peer, address). `status` prints when an address of ANOTHER carrier type is adopted. `notify_at` is covered by the request signature and accepted only from its signer (test).
### 3.4 Public TCP listener and any IP (M3; IPv4 only)
- Sansa's Q2 changes to my 2.4a numbers: keep 4 unauthenticated per /32 (release on every exit path), strikes 10/60 s -> 60 s doubling to 1 h; a connection that closed before the TLS hello is NOT a strike; one strike per connection; log counts only, never a stranger's address. Reserve 16 of 32 slots for PROVEN addresses: proven = admission-key hash found in the table AND a valid signature, recorded after `verify_strict`; the proven table is SEPARATE from the strike table; window 1 h (not 10 min), persisted across a restart; look the key hash up FIRST and verify the signature only on a hit (today both run: `same and good`, tcplink.py:469). Keep `PEER_PER_MIN` 3600 per agent loopback server. Pre-admission CPU (ECDSA P-256 per handshake) is bounded by 4 x 32 slots x 5 s: fine. Behind NAT or a proxy the limited address is the proxy's: say so in the docs.
- New from the human's questions today (2026-10-04): (a) `max_unauth` (32) is ONE counter for the whole carrier (tcplink.py:219, `_unauth`), so a flood on one door's port fills the pool for ALL doors: make it per door plus a global cap, with the per-IP rules above. (b) Beyond that, a distributed flood is the firewall's and the provider's job, not the application's: our job is to refuse unauthenticated connections as cheaply as possible (silent close, one deadline), and say so in the docs. (c) A public door (read/inbox) on Tor has NO client authorization (torlink.py `add_public_service`), so strangers can reach it; it relies on Tor's own defenses (`HiddenServiceEnableIntroDoSDefense`, `HiddenServicePoWDefensesEnabled`, `HiddenServiceMaxStreams 32` + CloseCircuit, torlink.py:245), the guest/blob proof of work and the door budgets. Peer and join doors are client-authorized (a join door by the throwaway key in the capsule). (d) On TCP the door fingerprint (`fp`) is the client's pin of the server (certificate pinning on top of TLS, CERT_NONE + spki hash); it does not keep strangers out, the admission key does.
- Cost of per-peer doors on TCP: one listening port per door; with the firewall closed that is moot for now; before any firewall port is opened the number of ports needed is (peers + public doors + open capsules).

### 6.1 The rule
- A node with SEVERAL carriers keeps running while at least one carrier is UP. A carrier that cannot start, died, or is being restarted is DOWN: the node serves and dials on the others. A node with ONE carrier, or whose every carrier is down, still exits (1) as today: nothing is left to serve with.
- A down carrier is retried with backoff for ever: 5 s, 30 s, 120 s (TOR_BACKOFF), and after TOR_RESTARTS = 3 restarts inside TOR_RESTART_WINDOW (1800 s) the retries slow to one per BACKOFF_SLOW = 600 s. A spent budget ends the FAST retries, never the node and never the retrying.
### 6.2 Start without blocking the loop (the TorNode.start main-thread constraint)
- Constraint (torlink.py:255-270): the `Popen` of tor must run in the MAIN thread (the child's death signal is tied to the forking thread). The long part is `wait_ready` (bootstrap, up to BOOTSTRAP_TIMEOUT), which needs no particular thread.
- So the loop (the main thread) does `carrier.start(wait=False)` (milliseconds: it only forks tor), and a NON-BLOCKING readiness check runs in every loop tick: new `TorNode.poll_ready -> "starting" | "ready" | "failed: <why>"` (the body of `wait_ready` for ONE pass: process alive, bootstrap line, hostnames/descriptors as today; BOOTSTRAP_TIMEOUT is a deadline kept by the node, not a sleep). `Carrier` gets a default `poll_ready` that returns "ready" (tcp has nothing to wait for), so the loop does not branch on the type.
- A restart is `stop` + `start(wait=False)` in the loop thread at the time the backoff says; the backoff is a timestamp the loop compares to the clock each tick, not a `sleep` (today `_recover_carrier` sleeps in 1 s slices inside the loop: that is what stalls tcp). `Doors.sync` for that carrier runs when the carrier turns "ready" (as `_recover_carrier` does after its start today).
### 6.3 Per-carrier state in the node
- `CarrierState` per carrier: `up` | `starting(since)` | `down(reason, next_try, tries, restarts[])`. One small class in noderun with a `tick(now)` that does the transitions above and returns what changed (so the loop logs "carrier onion: down (why); retry in 30 s" and "carrier onion: up" once per change).
- What a DOWN carrier switches off: (a) dialing: `MultiDialer` gets `usable(type) -> bool` and leaves a down carrier out of `_order` (this is the fast "not ready" skip that M1b left out) and out of the re-probe; if no carrier is usable for a peer the error is the usual "no address" / unreachable; (b) its `Doors.sync` (a down tor has no onion to serve: the doors' loopback listeners are stopped with it and re-created on "ready"; held doors and credentials are on disk and untouched); (c) its LocatorService (`_due` says nothing while down: an announcement over a dead carrier would only fail and back off).

Nothing else changes (fingerprint check through a second channel, one request per token, encrypted keys in the signed answer, grace, expiry, MAX_OPEN 8).

### 1. Capsule format v2 (decode_capsule / _check)
`join` becomes a LIST (1 or 2 entries, one per carrier type, no duplicates, issuer's order = dial order): `joins: [{"endpoint": E, "boot": B, "dial": D}, ...]`. `boot` = that join door's one-time bootstrap credential (secret half, or wrapped by the passphrase), `dial` = the throwaway public client key of THIS capsule for that carrier type (the joiner authorizes it on its own door for the owner). Each entry is checked as today (`check_endpoint`, boot/dial credential type == endpoint type). Everything else in the capsule is unchanged; `v` = 2. NO v1 compatibility (the human: nobody but us uses it; rollback = backup + old tag): before the deploy no capsule may be open (`capsule list`); a v1 block is refused with "re-issue". Size: a 2-entry capsule is about 1.6 KB, MAX_CAPSULE 6000 stays.

### 2. Owner: create
`capsule create THREAD [--carrier tcp|tor ...]` (repeatable; default: the primary only, exactly today's behaviour). For each listed carrier: new boot and dial credentials, a join door `join-<cid>` on THAT carrier (door names are per carrier), its address (`wait_address` per carrier). The record (`capsules.json`) keeps `types: [...]` and the door name is the same on each carrier. All-or-nothing: any carrier failing tears down the doors already made and the record (as today for one). Refused with the node's reason when a LISTED carrier is down on the running node (the existing `_node_says_down` check, per listed carrier): the human drops it with `--carrier`. Printed warning when the list has tcp: "this capsule contains a tcp address (your IP) next to ...; anyone who reads the block learns it; a capsule with only your onion address does not". `describe` (the joiner's view) lists the carriers.
Join doors on EVERY carrier of the set: `handlers` for kind join = the same JoinServer on each carrier's Doors (public read/inbox stay primary-only, not M2). `sweep` runs for every carrier (expiry, grace, orphan join doors, `door_gone` only when ALL carriers' doors are gone); `_teardown` closes `join-<cid>` on every carrier and drops the dial key files.

### 3. Joiner: accept
`capsule accept BLOCK --fingerprint ... [--carrier X ...]`: the carriers used = capsule types ∩ the carriers this node runs (∩ the `--carrier` flags if given, so a tor+tcp joiner can refuse to show its IP); none left = "this capsule needs one of {types}; this node runs {..}" (today's error generalised). For each used carrier: `use_credential(join endpoint, boot)`, a throwaway own credential (`mysecret/mypub`, one per carrier), OUR door `owner-<id26>` on that carrier authorized with the capsule's `dial` key of that type. `joins.json` record keeps `endpoints` (the capsule's list, issuer's order), `used` types, `mypub` per type, key files `join-<cid>-<type>.priv` (0600).

### 4. The request (owner side `_request`)
`join_request` carries `offers: [{"endpoint": my door address, "credential": mypub}, ...]` (replaces `endpoint`/`credential`), covered by the joiner's own signature as today. Owner checks: 1..2 offers, distinct types, each type is in the capsule record's `types` AND is a carrier we run, `check_endpoint`/`check_credential` per offer; anything else = `refused` (same answer as every refusal). The record stores `req.offers`.
Joiner timing (poll): send the request once at least one used carrier's door has an address; the others get 120 s after the first (a carrier that is down must not block the join; one that is merely slow still gets in). A joiner with one carrier up sends 1 offer: the owner gives 1 door.

### 5. confirm and the answer
`confirm` (owner's human): for EACH offer whose carrier we run: `_no_rebind`, `open_door("peer-<id27>", "peer", credential=offer.credential, agent=joiner)`, `use_credential(offer.endpoint, dial_secret_of_that_type, agent=joiner)`, `book.add(joiner, name, offer.endpoint, [thread])` (PeerBook.add ADDS one endpoint per type, H1 applies: the joiner's first address of the second carrier starts as not good). All idempotent steps, failure puts the record back to pending (a retry works), as today; then member_add; `owner_door` = the door name (same on each carrier).
`join_status` answer `joined`: `endpoint` becomes `endpoints: [one per carrier that has the door and an address, issuer's order]`, still signed (the signature covers the whole body). Joiner `_verify_joined` checks every endpoint (`check_endpoint`), then for each: `use_credential(ep, mine_of_that_type, agent=owner)`, `book.add(owner, name, ep, [thread])` per endpoint. The node loop does the rest (MultiDialer), a thread is never bound to a carrier.

### 6. Joiner poll transport
`transport_for(endpoint)` = the carrier of that endpoint's type (`noderun.carrier_for`/the carriers dict); the join_request/join_status go to the capsule's endpoints in the issuer's order, over the carriers the joiner uses, falling back to the next one on failure (same token: the owner answers the same joiner idempotently). Tor not ready yet = tcp still works. Both calls are already idempotent.

### 7. Not in M2
Public doors per carrier; `node init` flags; a capsule v1; cross-carrier address learning; any change to thread/event format.

## Rev 9 (2026-10-05 : M4, push on dial (M4a) and the notify address (M4b); design for Sansa's review, no code yet

Built from a read of the live code (sync.py `_handle`/`_answer`/`_authenticate`, `pull`, node.py `_run`/`on_notify`, mirror.py `ingest`, locators.py). Facts that shape it: a signed request already signs EVERY key except `sig` (`_req_bytes`), so an extra signed field needs no change on either side; an unknown request type for a thread the sender may read answers `error "unknown request type"` (a client treats `error` as a failed request, so the push client must never let that fail a pull); `summary` carries only `head` and `n` (a dialer learns what a peer holds only from the paged `list`, which `pull` already fetches); every request is its own connection (tcp.py), so "the connection" below means the one resolved transport of a pull; `pull` passes `live=False` to `Mirror.ingest` (pulled history is not author-rate-limited).

### M4a. Push on dial
1. Request `{"t":"push","thread":T,"events":[<canonical event dicts, dependency order>]}`, signed and `aud`-bound by `sign_request` like every sync request. Server: a branch in `_answer` after the thread gate and `_may_read` (so a thread we do not hold, or a non-reader, gets what it gets today), BEFORE anything is ingested: `request.thread == thread`; `from` is a CURRENT member whose role is not `observer` (membership as of now; a removed member is refused); `events` a list of at most `PUSH_MAX_EVENTS` (64) dicts; each `event.thread == T`; no genesis (push never creates a thread, never stores orphans); the whole request is already capped by MAX_REQ (64 KiB, about 48 KiB of events).
2. Ingest: each event through `Mirror.ingest(ev, live=False)` (same path as a pulled event: signature, thread rules, parking of events with missing parents, MAX_STORED, wake via `inbox.jsonl`). `live=False` = parity with pull: the per-author hourly rate rule does not apply to relayed or catch-up events; the limit that applies is the PUSHER's bucket below. Relay of other authors' events is allowed (every event is self-verifying).
3. Budget (Sansa's Q6): a token bucket per (peer, thread) on NEW accepted events (burst 200, refill 120/h); parked results count against the same bucket; a duplicate costs nothing; time budget per request about 3 s (the transport deadline is 8 s): events left when the budget or the bucket runs out are answered `deferred`, never ingested. The ordinary per-key request rate (`RATE_PER_MIN`) applies to the push request itself.
4. Answer (signed by `_reply`): `{"t":"pushed","results":[{"id":<event id>,"s":"accepted|duplicate|parked|deferred|rejected","why":<short reason or absent>}...],"retry":<seconds or absent>}`, one entry per event in order; `Result.status` maps: accepted/voided -> accepted, duplicate -> duplicate, pending/awaiting -> parked, rejected/conflict/invalid -> rejected with the reason.
5. Client: `sync.push(transport, me, tid, events, peer_id, ...)` and `Node._run`, `pull` branch: after a SUCCESSFUL pull the node computes `ours - peer_ids` where `peer_ids` is the id list the pull just fetched (`pull` returns it in its result, as a set, bounded by MAX_LIST_IDS), orders it by our own dependency order and pushes up to `PUSH_REQUESTS_PER_RUN` (4) requests; the rest goes next cycle. A `deferred` or `retry` answer is remembered per (peer, thread) and honoured. NEVER pushed: events the peer already lists; genesis. The push result is a NOTE on the job (`status` shows "pushed N, M parked"), never a failure of the pull. An answer `error "unknown request type"` (or any error, any exception) = "this peer does not push": cached per peer for 6 h, no retry in that time, the pull is untouched.
6. Result: an outbound-only member polls (dial, pull, push) and both directions flow over what it dialed; nothing needs to reach it. For two dialable nodes (today's pair) the push is redundant after the notify and costs one extra request only when there is a diff (duplicates cost nothing at the receiver).
7. NOT in M4a: blob push (a member that holds a blob serves it, blobworker already fetches from every member that holds one), push of keys (`key` stays a pull), any new door.

### M4b. The notify address (`notify_at`)
1. Config `node_config.json` `"notify_via": "tcp"|"tor"|absent` (CLI `sigilnet node notify-via tcp|tor|none`): the carrier type on which THIS node wants notifies. Absent = today (no field sent, notifies use the pull addresses).
2. Sender: when set, the node adds `"notify_at": {"type": T, "addr": A}` to the signed `summary` request of each pull and to its `notify` request, where `A` is the address of OUR peer door for THAT peer on carrier T (the door bound to that agent: the only door whose traffic is attributed to it); omitted when we do not run T or the door has no address yet. It goes to ONE host inside a signed request, never into a thread, never announced to anybody else.
3. Receiver: after `_authenticate`, for a sender in the peer book (the `on_inbound` seam): `on_notify_at(agent, field)`: ignored unless `{"type","addr"}` exactly, `check_endpoint`, we run a carrier of that type (a Tor-only node cannot adopt a tcp address: it stays anonymous, human rule), and that carrier's `locator_problem` passes (any IPv4 since M3; refuses loopback/link-local/multicast/own door/port < 1024). Stored in the locator book of that carrier type as the peer's NOTIFY locator (`notify` + `nfail`, apart from the pull locators, one per peer per carrier), changed at most once per 60 s per peer (LOCATOR_MIN_GAP), rewritten only when it changes. A request with a bad `notify_at` is still answered normally; the field is just not used.
4. Use: the `notify` job dials the notify locator first; if it fails or none is known it falls back to the pull addresses exactly as today (D2: "keep today's behavior"; never a regression to polling). 3 failures drop the notify locator (back to the pull addresses). A notify stays a hint with no text; one dial per peer per `NOTIFY_MIN_GAP` (30 s) on the notify address.
5. `status`/`peer list` show "notify tcp 1.2.3.4:47700 (adopted)" and a line when the notify carrier differs from the pull carrier (visibility, not a gate). No version gate: an old node ignores the key (verified on r45b by Sansa).
6. Result: the human's scenario (a Tor-pulling peer that takes its notifies over TCP, notify and pull on different carriers, M5 shape) without any new directory.

## Rev 10 (2026-10-05 : M4a built (branch m4a_push); what differs from rev 9
Built as designed with Sansa's P1-P5; differences and additions: (1) `sync.wire_enc/wire_item/open_wire` are the one seal and open step for `get`, `pull` and `push` (P1). (2) `PullResult["peer_ids"]` = the ids the peer listed; the node pushes `resolved - peer_ids - held` (P4). (3) The push request budget (6/min per sender, 24/min from known senders) is checked in `_handle` before the Mirror lock (P2); the bucket, the 8-reject cap and the 3 s wall-time budget are inside it; the answer carries `retry`. (4) `on_push(agent, thread, accepted ids)` is called after the lock is released; `Node.on_push` runs the `_after_pull` body (source excluded) (P5). (5) Node caches in memory: `nopush[peer]` 6 h, `push_off[(peer, thread)]` 1 h or the `retry`, `push_held[(peer, thread)]` rejected (until the admin head changes) / parked and unopened (1 h) (P4). (6) NEW, not in rev 9 (Sansa's optional Q5): an acknowledged notify that the peer does not answer with a pull of its own within `FOLLOW_WAIT` (20 s) makes the notifier pull that peer, whose push then carries what the peer lacks: otherwise an outbound-only node's change reaches a peer that cannot dial it only at its next 300 s pull. The server records `heard[peer]` (the time of its last non-ping, non-locator request) for the peers in the book; a peer that pulls back costs no extra request. (7) A result carries `id` when the event could be opened (an envelope has no id); unopened gives the epoch id as `why`. (8) An event bigger than PUSH_BYTES (48,000) is skipped by the client (the rule allows 64 KiB events; they travel by pull).


## Rev 11 (2026-10-05 : M4b built (branch m4b_notify_at, off m4a_push); what differs from rev 9
Built as designed with N1-N3.
