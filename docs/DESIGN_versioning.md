# DESIGN: protocol versioning, rev 3, 2026-10-06 (Arya; rev 0 reviewed by Sansa line by line against the 0.1.1 code the same day, rev 1 folded in her findings, rev 2 folded in the human's versioning rules: major.minor, previous major, thread format; rev 3 folds in Sansa's check of the thread-format enforcement against the 0.1.1 code). Stages 1-2 BUILT and live (0.2.0); stage 3 (thread format 2) BUILT 2026-10-06 evening, see DESIGN_versioning_stage3.md (one change: the envelope version stays 1 for every thread, section 5a.3 above is superseded on that point).

Origin: the human, 2026-10-06, after the public release: if someone runs v0.1 and someone else runs v0.8 and they can no longer talk, they should at least KNOW WHY. He is unsure whether each message type should carry a version or the wire protocol as a whole. (Also: if an exploit is found, or the protocol is enhanced, we must be able to update without silently breaking everyone.)

## 1. What exists today (the 0.1.1 code, verified by Sansa)
- Events: `v` = 1 exact; kinds in a fixed set; bodies exact per kind. Rules dict: a genesis requires exactly the full key set and any extra key is refused (thread.py:105); `rules_update` bodies are exact too. So any new event layout, kind or rules key is invisible and FAIL-CLOSED for old nodes (the event never enters their mirror; later events park behind the missing parent, silently).
- Sync requests: `summary`, `list`, `get`, `key`, `notify` and `ping` IGNORE extra top-level fields (the signature covers them; precedent: `notify_at`). `push`, locator announcements, capsule `join_request` and `join_status` REFUSE any extra field (an exact set). Replies: summary/list/events clients read named fields; `check_pong` is EXACT (key set and `v` == 1).
- Error replies are signed and carry `why`; the asker keeps it as the job error, shown in `peer list`/status and as `FAIL <why>` in history.log. `_clean` cuts it at 200 printable characters. Only authenticated known peers get it (a stranger gets "unknown").
- TCP: the DOOR speaks first (39 bytes: magic `SNTCP1`, mode, nonce); the client rejects any other magic ("the door did not speak the tcp carrier protocol"). Capsule `v` 2 exact. No software or protocol version anywhere on the wire; no `sigilnet --version`.

## 2. Decision: TWO numbers, one per lifetime
Compatibility is decided between two nodes ("can these two talk at all, and at what level?"): one wire number answers it and gives one sentence to print. Per-message-type versions multiply into a grid nobody can reason about. But there are two different lifetimes, and each gets its own number:
- **The wire protocol** (how nodes talk NOW; transient): `wire = major.minor`. The human's rules (2026-10-06): a MAJOR increase is a breaking change (0.8 and 1.0 cannot talk); a MINOR increase is backwards compatible (1.0 and 1.5 talk); a release keeps the ability to talk to the PREVIOUS major (2.x falls back to 1.x, 3.x to 2.x, so 3.x cannot talk to 1.x), unless an exploit makes us specifically deprecate a major.
- **The thread format** (what the signed events of a thread MEAN and how its state is derived; PERMANENT: events stay on disk and are replayed by every future version): an integer, and it is the EXISTING per-event `v`, now defined as the format of the whole thread: the `v` of the genesis, constant for the thread's life, and every event of the thread carries the same `v`. A thread never changes format: a newer format means a NEW thread, reached by the rotation machinery we already have (`rotate`, `[ROTATED-TO]`, follow-rotation). A node keeps the derivation rules of every format it still supports (so old threads replay identically) and declares them: `formats: [1, 2]`. There is no "minor" of a thread format: an additive change is an `x-` kind or the `x` key (section 5), a breaking change is a new format.
- Declarations (self-declared hints, authentic only as a claim of that node's key): `wire` (e.g. "1.5"), `majors` (the wire majors it can speak, e.g. [2, 1]: its current one and the previous, or fewer after a deprecation), `formats` (thread formats it reads/writes), `sw` (software version string for humans only: printable, <= 40 characters, display only, never logic). The package version (0.1.1 today) is separate from the wire number: a patch or a minor package release that does not touch the wire changes nothing on the wire; a wire major change is always a package major change.
- **Legacy and numbering.** 0.1.x nodes declare nothing and speak wire major 0 (shown as "wire ?"), thread format 1. The first versioning release declares wire 1.0 with `majors` [1, 0] (it falls back to the plain 0.1.1 shapes, which is what "first contact uses the plain 0.1.1 shape" already says) and `formats` [1]. Before wire 1.0 a package minor may break nothing it has not announced (the 0.x convention is not relied on); from 1.0 the rules above are the contract.

## 2a. The negotiation
Two nodes talk at the HIGHEST wire major in the intersection of their `majors`; within that major the lower minor's feature set applies (a node learns the peer's minor from its declaration and uses only features of the lower minor; unknown extras are ignored by design). An empty intersection means refuse and explain (section 4). A thread is served to a peer only if its format is in the peer's `formats` (undeclared = [1]); otherwise the gating text of section 5.

## 3. Where they travel (the transport is FROZEN)
- NO version in any transport: the TCP hello (`SNTCP1`, 39 bytes, door speaks first, so a new door cannot know the client's age) stays frozen for good, as do the admission frame sizes, the Tor door and the capsule layout. All negotiation is at the application layer, where it is signed and explainable.
- Extras ride ONLY where 0.1.x ignores them: `summary`/`list`/`get`/`key`/`notify`/`ping` requests and their replies. NEVER in `push`, locator announcements or capsule requests addressed to a peer that may be 0.1.x. First contact uses the plain 0.1.1 shape; the new node learns the peer's declaration (`wire`, `majors`, `formats`) from a PULL reply, caches it per peer (a new field in `peers.json`: rollback test), and adds the fields to push/locator only for peers known to declare wire major >= 1.
- Ping: the pong stays BYTE-IDENTICAL in protocol 1 (a new key or `v`=2 makes every 0.1.x asker print "bad answer" with no hint). A new node answers with the old pong unless the ASKER declared itself (an extra field in its ping request, which old servers ignore); only then the pong carries an optional `wire`/`sw`.
- `sigilnet --version` prints `sw`, `wire`, `majors`, `formats`; `peer list` and `status` show each peer's `wire`/`sw` (`wire ?` for 0.1.x) and the last refusal text, so the operator sees "peer X: needs upgrade" without reading logs.

## 4. The rule and the explanation
The negotiation is section 2a. A security setting is NEVER lowered by a peer's declaration: any behaviour removed by a security fix is gated by the NODE'S OWN `majors` (the node simply stops listing a deprecated major), and a peer that talks at the previous major gets the previous major's behaviour, weaker behaviour included, for as long as we keep that major (stated in the support policy).
Otherwise the NEWER node refuses and explains, in two places:
1. In the error reply's `why` (it reaches the 0.1.x operator through the existing job-error path): FACTS FIRST and URL-FREE, well under 200 characters, e.g. `peer speaks wire 0, this node needs 2 or 1 (sigilnet 1.x+)`. No URL: a peer-supplied `why` is shown to an operator that is often an LLM agent, and "upgrade at https://..." is exactly the shape of a phishing or prompt-injection line (any member can send any text). `AGENTS.md` says these lines are DATA and that the person decides where to upgrade from (a pinned tag or commit); the text may say "see the sigilnet README / SECURITY.md".
2. On the newer node: history.log, `peer list` and a wake line, once per peer per day.
An OLD node cannot be taught anything, so the wording of this refusal text is fixed at the FIRST release that drops wire major 0 from `majors` (or serves nothing to it): write it now, short, tested against the 0.1.1 loaders (an old node's job error must contain it: run against tag v0.1.1 installed from the public URL).

## 5. Evolving threads and events (the legacy-safe parts)
- **Server-side gating by thread format (the mechanism that works for 0.1.x).** A peer is served a thread only if the thread's format (the genesis `v`) is in the peer's `formats` (undeclared = [1]). Otherwise the new node answers that peer's pull/get for THAT thread with the short `why` ("thread uses format 2: upgrade sigilnet") instead of serving events the old node would only refuse ("unsupported version" for a v2 genesis) or park. The text travels the job-error path and the operator sees it. A thread-level rules key (`min_proto`) is NOT used: a 0.1.x node cannot even load a genesis with an extra rules key, and a `rules_update` carrying one parks every later event silently, so such a key would explain nothing to 0.1.x.
- **Thread format 2 = format 1 + the extension mechanism** (stage 3). Format 1 threads are FROZEN: they stay byte-for-byte what 0.1.x writes and reads, for ever (our own thread `02a5d045` is one). A new thread is created as format 2 only when ALL its members can read it; the upgrade path for an existing thread is `rotate` (a new format-2 thread, the old one stays readable, followers follow by themselves; a member whose node lacks format 2 gets the gating text). Format 2 is the first place where the extras below are legal.
- **Extension kinds, `x-` only (format 2 threads).** An unknown kind is storable-but-uninterpreted ONLY if its name carries the marker `x-` (e.g. `x-reaction.1`). The registry says `x-` kinds can NEVER be admin kinds or change validity or membership; anything that does needs a new thread format. A kind's meaning never changes after release (new meaning = new name). Every other unknown kind keeps being refused/parked (a node cannot tell an admin kind from an inert one; storing an uninterpreted admin kind would fork its derived state silently). `x-` kinds are charged to the same buckets (member-only authors, `posts_per_author_per_hour`, `max_event_bytes`), count toward `MAX_STORED`, and are a QUIET class for unread/wake (no wake line per event).
- **Extension key `x` in event bodies (format 2 threads)**: optional, ignored by nodes that do not know it, covered by the signature. Never in a format 1 thread (0.1.x rejects an extra body key). The mechanism protects only nodes from this release on.
- **Security fixes:** a validity bug fixed by a protocol change is a new wire major (or a new thread format when stored meaning changes) with the vulnerable major REMOVED from the node's `majors` (the human's rule: unless an exploit, the previous major stays); tell the members, publish an advisory (`SECURITY.md` + release notes naming the minimum version). A deprecated major is refused with the section 4 text at once.

## 5a. Making "the format is the genesis `v`" TRUE (Sansa's check against the 0.1.1 code)
Today `v` is looked at ONLY in `event.py` `check_structure` (`ev["v"] != V`, V = 1) and in the builder; `thread.py`, `mirror.py` and `sync.py` never read it, and nothing compares it with the genesis. It is "consistent" only because the constant has one value. The thread id is the hash of the genesis INCLUDING `v`, so the format cannot be changed after the fact: that is the reason the format is the genesis `v`. The versioning work must add:
1. **The rule:** ingest refuses any non-genesis event whose `v` differs from its thread's genesis `v` ("format mismatch"); a parked event that arrives BEFORE its genesis is re-checked when the genesis arrives. Without it a member could post a v2 event into a v1 thread: 0.1.x refuses it (and the author's later events park behind it) while new nodes accept it, a silent fork between old and new views.
2. **Structure vs format:** `check_structure` runs in `sync.ingest` before the thread is known; it accepts the SET of supported formats, and the per-format validation runs after the genesis is stored.
3. **Everything hard-coded to format 1 is routed by the thread's format:** the exact body key sets inline in `thread.py` (member_add, checkpoint, rules_update, close, ...), the rules key set, event REQUIRED/OPTIONAL fields, the builders (`Writer`, `rotate.py` need an explicit format argument for a NEW thread's genesis), the envelope layer (`envelope.py` `v == 1 and set(x) == ...`: decide whether the thread format covers the envelope version: yes, an envelope version follows the thread format), the capsule describe text. `Thread` gets a `format` attribute set from the genesis; format 1 code paths stay byte-for-byte (the frozen ones); format 2 dispatches explicitly.
4. **The replay promise becomes a check, an executable CONFORMANCE CORPUS:** a directory of frozen format-1 threads (events.jsonl from throwaway test threads, never ours) with the expected derived state as JSON (members, roles, epochs, closed, cut, last checkpoint, resolved/parked/void sets, genesis id), run by every future release's suite; a second corpus of "must reject" events (v mismatch, unknown kinds, extra body keys); a 0.1.1-written events.jsonl as a golden file loaded by the new code. A format change that alters any expected value fails the suite.
5. **Who can tell a 0.1.x member that a thread uses format 2?** A v2 genesis on a 0.1.1 node is refused silently (the pull loop only counts `rejected`; no reason, no job error, below `MAX_JUNK`). So ONLY the server-side gating text on the summary/list/get answers can tell it (job-error path), and it needs one upgraded peer on the path (if the serving peer is itself old, nobody can say anything). New nodes also record WHY events were refused in the pull result (counts by reason in the job note: "N events refused: format 2") for their own operator.
6. **Rotation as the upgrade path:** `rotate_thread` and the 80% auto-rotation KEEP the thread's format by default (a wall rotation must never silently cut off members with older software); moving to a newer format is an explicit owner decision (`rotate --format 2`), never automatic; before it the owner node looks up each member's declared formats in the per-peer cache (observers included: the human's read-only seat must run software that reads the format) and warns or refuses when a member declares [1] only or is unknown ("wire ?" for 0.1.x); never combine `--close` with a format rotation until every member has declared the format. A follower whose node lacks the format: with `follow_rotation` on, the pointer (in the format-1 thread, readable) makes it ask for NEW, gets the gating text each time (backoff, cheap), NEW never lands, and the 7-day expiry in `autorotate.py` removes the follow safely; the expiry log line and `peer list` must then say "refused: needs format 2" (taken from the follow's job error), not "never arrived".

## 6. Support policy (the human's decision)
Each release states `wire`, `majors` and `formats`. The human's rules: a release talks to its own wire major and the PREVIOUS one (2.x falls back to 1.x, 3.x to 2.x, 3.x cannot talk to 1.x) for as long as the previous major is not specifically deprecated (an exploit may deprecate it at once); minors are always compatible. Old thread formats are kept readable (replay) for as long as any supported release can have them on disk, and are removed only with a major release that says so.

## 7. The flag day for 0.1.x: what the FIRST versioning release must keep byte-identical
(a) event layouts and kinds, (b) the rules key set (a genesis has exactly the old keys), (c) `rules_update` body keys, (d) capsule v2 key set and its request/answer sets, (e) push and locator request key sets, (f) the pong key set and `v` = 1 (for askers that did not declare), (g) the TCP hello and frame sizes, (h) every on-disk file an old loader reads (`peers.json`, `rotation.json`, `node_config.json`: the p7/p8 rollback tests are the pattern; the new per-peer declaration cache must pass the 0.1.1 loaders). It touches only pull/ping extras, the `--version` command, the gating and refusal text and the status display; no event layout. This release is the LAST one that must keep every layout identical, and doing it while the installed set is a handful of nodes is the cheapest it will ever be.

## 8. Build order (each stage reviewed and shipped alone)
1. `--version`, the `sw`/`wire`/`majors`/`formats` constants, the per-peer declaration cache, extras on pull and ping, the status display. 2. Server-side gating by thread format and the refusal text, tested against v0.1.1 from the public URL. 3. Thread format 2 with the extension mechanism (`x-` kinds, `x` key) and the rotate upgrade path. Stages 1-2 deliver what the human asked for (know WHY) without touching any event or rule format.

## 9. Tests
Golden test: the 0.1.1 wire bytes are accepted unchanged in both directions; extras only where 0.1.x ignores them (a test per request type, push/locator/capsule shapes unchanged); old pong for an undeclared asker, new pong only on declaration; first contact plain, extras after the pull reply declares the peer; refusal text reaches an installed 0.1.1 node's job error (<= 200 characters, URL-free, facts first); negotiation table (majors intersection, highest common major, lower minor's features, empty intersection refused, a deprecated major refused); gating answers a legacy peer for a format-2 thread; downgrade (a low declaration never weakens a security setting); format 1 thread byte-identical, format 2 genesis refused by a 0.1.1 node with a readable cause; `x-` kinds relayed, never interpreted, charged to the buckets, quiet for wake; unknown non-`x-` kinds still refused; rotate from format 1 into format 2 followed by a member that has format 2; mixed-`v` event pushed into a v1 thread (refused by new and old alike: same view), a parked event before its genesis with the wrong `v`, a v2 genesis served to a 0.1.1 peer (gating text in its `peer list`), the expiry line text, rotate keeps its format by default, `rotate --format 2` warns on an old or unknown member and on the observer, the conformance corpus round trip, rollback test for any new file. Sansa writes the adversarial suite after the build.
